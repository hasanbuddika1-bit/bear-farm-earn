Build a production-ready, security-first Telegram Mini App earning platform using React, TypeScript, Firebase Authentication, Cloud Firestore, Firebase Cloud Functions, and Firebase App Check.

The application must be designed for approximately 10,000 daily active users. Security, data integrity, anti-fraud protection, and reliable database performance are the highest priorities.

1. Critical security architecture

Use a zero-trust architecture.

The frontend must never be trusted for security-sensitive operations. All important actions must be processed and validated by a secure backend using Firebase Cloud Functions.

Never store Firebase Admin SDK credentials, service account keys, private API keys, or other secrets in frontend code, GitHub, or client-side environment variables.

Use Firebase Admin SDK only in trusted server-side Cloud Functions.

The frontend must not directly modify user balances, referral rewards, withdrawal status, admin roles, or other sensitive fields.

2. Firebase Authentication and Telegram verification

Implement secure Telegram Mini App authentication.


Verify Telegram initData on the backend using the Telegram bot token.

Never trust Telegram user ID, username, or other user data sent directly from the frontend.

Verify the initData signature and expiration.

Create or retrieve the authenticated Firebase user only after successful verification.

Prevent forged authentication requests.

Use Firebase Authentication custom tokens or another secure server-side authentication flow.

Do not use a client-supplied user ID as proof of identity.



3. Firestore security rules

Create strict Firestore Security Rules using deny-by-default principles.

Users must never be able to directly write or modify:


coin balances

total earnings

referral rewards

referral counts

ad completion records

withdrawal status

withdrawal approval or rejection

admin roles

account suspension status

fraud scores

system configuration

reward codes

other users' private data



Sensitive operations must be performed only by trusted Cloud Functions.

Users may read only their own permitted profile and transaction history. Do not expose the entire users collection or private data.

Admin access must be verified server-side using custom claims and backend authorization. Never rely on a hidden admin button, frontend route, email field, or localStorage value for admin security.

4. Secure admin panel

Build a separate protected admin panel.

Requirements:


Admin access must require verified Firebase Authentication.

Verify admin custom claims on every sensitive backend request.

Never grant admin privileges based only on a frontend variable.

Never allow users to assign themselves an admin role.

Use least-privilege access.

Protect admin routes and backend endpoints.

Add an admin audit log for every important action.

Log admin ID, action, target user ID, timestamp, and relevant changes.

Support secure user suspension and unsuspension through backend functions.

Admin operations must use server-side validation and authorization.



The admin panel must not expose all user data unnecessarily. Use pagination, limited fields, and role-based access.

5. Anti-cheat coin system

The coin system must be server-authoritative.

Never calculate or permanently award coins based only on frontend JavaScript.

Create a secure reward ledger.

Every reward transaction must contain:


unique transaction ID

authenticated user ID

reward type

reward amount

server timestamp

source reference

status

fraud-check result



Use Firestore transactions or another atomic mechanism to prevent duplicate rewards and race conditions.

Implement idempotency keys so that repeating the same request cannot award the same reward multiple times.

A request must not be able to choose an arbitrary reward amount. The backend must determine the reward from trusted server-side configuration.

Prevent:


negative or manipulated coin values

duplicate reward claims

replay attacks

concurrent double claims

forged reward requests

unauthorized balance changes

client-side balance manipulation



Maintain an immutable or append-only reward ledger where practical. Never rely only on a mutable balance field without transaction history.

6. Watch Ads anti-fraud protection

Implement a secure ad reward verification system.

The frontend must not be able to claim that an ad was watched successfully.

Only award coins after receiving a trusted, verifiable ad network callback, server-to-server verification, or another supported provider verification mechanism.

If the ad network does not provide a verifiable completion callback, do not treat a frontend callback alone as proof of a completed ad.

Requirements:


Generate a unique ad session ID on the backend.

Track ad session start and completion.

Validate the session server-side.

Prevent reuse of completed sessions.

Prevent replay of reward requests.

Rate-limit ad sessions and reward claims.

Reject impossible or suspicious activity.

Store reward records with unique IDs.

Never accept arbitrary reward amounts from the client.



Do not claim that browser-side timers, disabled buttons, or JavaScript checks can fully prevent ad fraud. Use provider-supported verification wherever available.

7. Referral anti-fraud system

Implement server-side referral tracking.

Requirements:


Validate referral relationships on the backend.

Prevent self-referrals.

Prevent referral loops and circular referral relationships.

Prevent duplicate referral rewards.

Use unique referral reward transaction IDs.

Do not award referral rewards merely because a client sends a referral code.

Require legitimate qualifying activity according to the configured referral policy.

Validate referral reward limits server-side.

Detect suspicious repeated registrations, device patterns, IP patterns, and rapid referral activity where lawful and appropriate.

Do not expose private referral data belonging to other users.



Referral rewards must be processed atomically and must not be awarded twice due to repeated requests.

8. Reward code security

Reward codes must be validated by Cloud Functions.

Requirements:


Store codes securely in Firestore.

Never hardcode private admin codes in frontend JavaScript.

Validate code status, expiry, usage limits, and eligibility server-side.

Prevent duplicate claims.

Use atomic transactions for limited-claim codes.

Prevent users from changing reward amounts.

Record every successful and rejected claim.

Do not expose all unused codes to the frontend.



9. Withdrawal security

Create a secure withdrawal workflow.

The frontend may submit a withdrawal request, but the backend must validate:


authenticated user

available balance

minimum withdrawal amount

withdrawal method

valid wallet or payment details

duplicate pending withdrawals

account restrictions

fraud status

sufficient balance



Use an atomic transaction to reserve or deduct the withdrawable balance exactly once.

Withdrawal status must be controlled by backend functions and authorized admin actions only.

Never allow the frontend to mark a withdrawal as paid, approved, rejected, or completed.

10. Data privacy and data leak prevention

Protect all private user data.

Requirements:


Users can access only their own permitted data.

Admins can access only the data required for their role.

Do not expose private user fields in public leaderboard APIs.

Do not return sensitive fields unnecessarily.

Do not expose Firebase configuration secrets or service account credentials.

Avoid logging passwords, authentication tokens, wallet secrets, or sensitive personal data.

Use server-side validation for all API inputs.

Sanitize user-provided text displayed in the admin panel.

Prevent unauthorized collection-wide reads.

Add appropriate retention and deletion policies.



Firebase client configuration values are not secret credentials by themselves, but Firestore rules and backend authorization must protect the data.

11. Database performance and read optimization

Design the database for approximately 10,000 daily active users.

Requirements:


Avoid reading the entire users collection.

Load only the authenticated user's required data.

Use pagination for admin tables and transaction history.

Avoid unnecessary real-time listeners.

Use efficient indexed queries.

Use cached or precomputed statistics where appropriate.

Use Cloud Functions for sensitive writes.

Prevent unbounded queries.

Monitor Firestore reads, writes, storage, and Cloud Functions usage.

Add Firebase budget alerts and usage monitoring.

Handle quota errors gracefully without losing transactions.



12. Rate limiting and abuse prevention

Implement backend rate limits for:


login and Telegram verification

ad sessions

reward claims

referrals

reward code claims

withdrawal requests

admin operations



Use server-side rate limiting and abuse detection. Do not rely only on frontend cooldown timers.

Consider Firebase App Check, authenticated callable functions, request validation, and a suitable server-side rate-limiting mechanism.

13. Secure implementation requirements

Before finishing:


Create the required Firestore data model.

Create secure Firestore Security Rules.

Create Cloud Functions for all sensitive operations.

Use Firebase Admin SDK only on the backend.

Add validation for every callable function.

Add duplicate request protection.

Add audit logging.

Add unit tests for security rules and reward functions.

Add tests for duplicate ad claims, referral abuse, concurrent reward requests, unauthorized admin access, and withdrawal manipulation.

Do not use demo security, fake protection, or client-only security.

Do not claim the app is unhackable.

Clearly identify any security feature that requires a real external provider, backend secret, or production configuration.



The final application must be secure by design, scalable, maintainable, and ready for a proper security review before handling real user balances or withdrawals.
